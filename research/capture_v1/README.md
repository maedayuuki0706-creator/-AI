# 研究専用・段階的データ収集 v1

本番取得・予想・配信モジュールを呼ばず、外部の独立ディレクトリへ保存する手動起動の収集器です。自動実行、Actions、Render、Discord、X への接続は追加していません。研究ブランチのみで運用を検証します。

## 収集と固定

| 段階 | 内容と条件 |
| --- | --- |
| 事前準備 | 公式出走表の6艇・締切を確認。指定DBを読み取り専用で結合。出走表は最大5分再利用 |
| 展示待ち | 締切1時間前から展示公開を確認。取得試行は失敗時も60秒以上間隔を空ける |
| 展示後更新 | 全6艇の展示タイムと展示進入が確認できた場合だけ展開版を保存。展示ST、風速、水面情報、欠測、取得時刻も記録 |
| 固定 | 締切4〜3分前に固定。直前90秒以内の保存済み入力があれば追加HTTPなしで固定。取得終了時と保存時にも時計を確認 |
| 間に合わない | 展示未公開・締切変更・遅延・不正原本を記録。締切3分前を過ぎて新しい事前予想を作らない |
| 事後照合 | 締切3分後以降に公式結果を取得。未確定なら120秒以上待つ。固定予想を変更せず別ファイルにレビューを保存 |

取得の時刻は「取得できた時刻」であり、公式の公開開始時刻ではありません。展示進入・展示STは本番の進入・STを保証しません。全艇の勝ち筋・負け筋と連動は scenario_v2 の条件分岐として扱います。

## 取得元と不足

- 公式 `racelist` / `beforeinfo` / `raceresult` を分離し、結果は事後工程だけで取得します。各リクエストはタイムアウト6秒、応答最大2MB、間隔2秒以上です。
- 指定された既存研究原本が90秒以内なら、レースID・締切・展示・ダイジェスト・チェックポイントを確認して再利用します。既存取得を呼び出したり、元ファイルへ書き込んだりしません。
- 任意の共有キャッシュは `<race_id>/<kind>.json`（`race_id`, `url`, `fetched_at`, `html`）形式。60秒以内・同一URL・同一レースの原本だけ再利用します。通常の既存キャッシュとこの形式が異なる場合は自動変換しません。
- `--fetch-foot` は公開足タイム取得を別プロセス・上限12秒で試行します。締切5分前以降は新規試行しません。6艇の選手IDと開催日・場・Rを照合し、0/-1等は欠測扱い。トークンや個人メモは保存しません。
- DB選手履歴は観測値として保存します。モーターの使用開始・集計日を記録しますが、公式の当該使用期間との一致は未確認と明記します。ST分布、前日からの足変化、水面別の追加履歴集計は未実装です。
- 独立取得だけの場合、現行新ゆうきの買い目や確率がないので捏造しません。比較可能な現行原本があるケースと区別して評価する必要があります。新しい勝率・展開確率・期待値は生成しません。

DBは `meta.json` の `snapshot_at`、選手IDキーの `players.json`、`場コード:モーター番号` キーの `motors.json` を読みます。実際の入力DB形式は接続前に照合してください。

## 起動

対象レースを公式の締切と照合したJSON配列で指定します。例の日時は形式説明用です。実際の当日レースに置き換えてください。自動の対象レース発見は未実装です。

```json
[{"day":"20990101","jcd":"04","rno":1,"deadline":"12:00"}]
```

リポジトリ直下から実行します。出力先はリポジトリ外、すべての入力データと別のパスであることを強制します。

```bash
python3 -m research.capture_v1.run \
  --manifest /absolute/research/races.json \
  --out /absolute/research/independent_state \
  --watch
```

任意で `--db-root`、`--fusion-root`（predictions/checkpointsを持つ研究データルート）、`--shared-cache`、`--fetch-foot` を指定できます。`--cycles 2` などで有限回の試行も可能です。30秒ごとに対象を巡回し、各取得の待機間隔を別に守ります。単一プロセスの順次処理なので、大量レースでは全レースの最終固定を保証できません。選定した少数レースから時間余裕を測定してください。

日付を偽って過去レースのlive予想は作成できません。日付が変わった後も、既存の固定予想のレビューのみ締切後48時間まで継続できます。検証用replayは別保存領域へ分離します。

## 保存・証跡

`<out>/<YYYYMMDD_JJ_RR>/` の `preparation/`、`revisions/`、`forecast.json`、`result.json`、`review.json` は排他的な新規保存です。`status.json`、`source_state.json`、`latest_data.json` は研究側の作業状態です。レース単位の非ブロックロックと中断再開を備えます。HTTPの生HTMLは新規永続保存せず、解析値・取得元・観測時刻を保存します。

固定予想とlocal_receiptはローカル時計による証跡です。`remote_checkpoint_verified=false`、エンジンの `prospective_uncheckpointed` のままです。第三者的な締切前の永続チェックポイントは未接続なので、これだけで検証済み前向き実績とは主張しません。返還・事故・不完全着順等は通常的中率/ROIから分離します。

## 検証（2026-10-16）

```bash
python3 -m unittest discover -s research/capture_v1/tests -v
python3 -m unittest discover -s research/scenario_v2/tests
python3 -m unittest discover -s research/scenario_v1/tests
```

収集23件、v2回帰35件、v1回帰4件成功。模擬時計による展示待ち→更新→固定→別保存レビュー、キャッシュ再利用時のHTTPゼロ、取得遅延、失敗後の待機、将来データ拒否、締切変更、結果混入防止、日付またぎ、固定後不変、中断復旧を確認しました。公式保存済みHTMLでも6艇抽出と結果解析を確認。展示前・締切表欠落の断片は欠測として拒否します。

この環境で公式への直接HTTP試行はタイムアウト、足情報の直接試行はHTTP 502でした。保存済みHTMLと模擬通信のテストは実サイトの連続取得の代わりにはなりません。常時稼働は開始していません。次の優先作業は、独立した実行環境で少数対象の取得・時刻・締切照合を通し、収集遅延と欠測率を測定し、外部チェックポイントを付けて前向きの全艇展開LOGを蓄積することです。今回の実装による的中率・ROIの改善実績はまだありません。
